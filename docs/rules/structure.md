# 構成・構造規約

### 概念の表現
- 概念はディレクトリで表現する
- 概念ディレクトリ（domain/）では型/定数/関数を共通のファイル名で分割する（types.ts / consts.ts / scripts.ts）

## ディレクトリ構成
### UIコンポーネント
- ui/
  - Reactコンポーネントを配置
- ui/entity/
  - domainに依存するコンポーネントを配置
- ui/parts/
  - 再利用可能な小さなコンポーネントを配置
  - domainに依存しない

### ドメインロジック
- domain/
  - クリーンアーキテクチャの entity 層に対応
  - 配下に各概念ごとのディレクトリを作成する

#### domain/ に置いてよいもの
UI・特定ユースケース・特定ページから独立した「概念そのもの」だけを置く。

- エンティティ / 値オブジェクト（マジックナンバーは consts.ts に value object として定義）
- 業務ルール・不変条件（バリデーション、計算ロジック）
- ドメインモデルの型定義
- 汎用的なバリデータ・ユーティリティ（適切な概念ディレクトリに配置）

#### domain/ に置いてはならないもの（UI・ユースケースの関心事）
定義が UI / 特定ユースケース / 特定ページに依存するなら、
定数・型・関数のいずれであっても domain ではなく利用側（UI / ページ定義側）に置く。

- 表示ラベル・画面コピー・「どう表示するか」を表すデータ
  - 例: ステータスごとの表示文言マップ、バッジの色定義
- 表示整形関数（表示用文字列を返すもの）
- view-model 型（特定のページ / フォーム / UI が必要とする形のデータ型。共通 UI 用でも不可）
- 特定ユースケース前提・特定ページ前提の型定義 / 文言

#### 判定に迷ったら
「この定義は、UI やページが一切なくても意味を持つか？」で判定する。
- Yes → domain/
- No（表示・入力・特定画面の都合が混ざる） → 利用する UI / ページ側

### データ
- data/
  - クリーンアーキテクチャの data 層に対応
  - 外部 API やデータベースとのやり取りを担当
  - 配下に各概念ごとのディレクトリを作成する

#### data/ に置いてよいもの
- **1 つの関心ごと（概念）に対するデータ取得・更新関数のみ**

#### data/ に置いてはならないもの
- 複数の関心を組み合わせて特定ユースケースを満たす「合成データ関数」
  - 合成は app 側（ルート / サーバーアクション）で、単一関心の data 関数を組み合わせて行う
  - 例:
    - NG: `data/dashboard/getDashboardData()`（ユーザー＋通知＋集計を内部で結合）
    - OK: `data/user/getUser()` と `data/notification/getNotifications()` を app のルートで並列取得して合成
