# コーディング規約

## TypeScript
### 関数
- 関数型プログラミングスタイルで実装する
- 破壊的なメソッドは使用しない
- 関数は小さく、副作用を持たせない
- アロー関数のみを使用する
- pushメソッドは使用しない
- forループは使用しない
- forEachは使用しない
- map/flatMap/reduceを優先的に使用する
- 関数の引数は必ずObjectでまとめる（引数が1つで意味が自明な場合は例外として許容する）
- `let` は使用しない。`const` で代替できる設計にする
- 配列の生成には `Array.from` を使用する

### 型定義
- 型定義は `type` を使用する
- 配列型は `Array<T>` 形式を使う
- 配列型の場合初期値は空配列 `[]` を使いOptionalにしない
- 公開するメインコンポーネントのProps型は `Props` を使用する
- 同じリテラル型を複数箇所で記述しない（type aliasを定義して参照する）
- 既存の型から派生させる場合はインデックスアクセス型（`User["id"]`）を使用する
- 型推論が効く場合は明示的な結果型を定義しない

### null / undefined
- `null` は使用しない。値の不在は `undefined` で統一する
- DOM API等が `null` を返す場合は境界で `?? undefined` に変換する
- コンポーネントの早期リターンで「何も描画しない」を返す場合は `return null` を使用する
- JSXの条件レンダリングでは `condition ? <X /> : null` ではなく `condition && <X />` を使用する

### JSDoc / コメント
- exportする型定義・関数・定数・コンポーネントにはJSDocを書く（関数の説明のみで良い）
- 複雑かつ重要な関数には処理手順ごとにインラインコメントを付与する

## Next.js
- App Routerを前提とする
- UIとドメインロジックを分離する
- page.tsx / layout.tsxではexport defaultを使用し、それ以外ではexport constを使用する

# React
- 公開するメインコンポーネントは`index.tsx` に書き `export` する
- メインからのみ使用するローカルコンポーネントは `index.tsx` 内に `export` なしで書く
- コンポーネントの型定義（Props等）や定数は `index.tsx` に同居させる
- `index.tsx` が肥大化しそうな場合は同階層に `ComponentName.tsx` で分割する
- ファイル内の記述順序は以下の通りとする
  1. import 文
  2. 定数定義（あれば）
  3. `type Props`
  4. export するメインコンポーネント
  5. ローカルコンポーネント
- 特定のコンポーネントでのみ使うサブコンポーネントは、親コンポーネントのディレクトリ内に配置する
- `React.memo` はパフォーマンス問題が確認された場合のみ使用する
- セマンティックHTML要素（`<li>` 等）のラップは呼び出し側で行い、子コンポーネントはリスト文脈等を知らない設計にする
- 既存の共通UIコンポーネントを積極的に再利用する

### Props設計
- `ComponentPropsWithoutRef` 等によるProps丸受け（スプレッド型）は使用しない。必要なpropsを個別に定義する
- 派生状態を別propsにしない（例: `errorText` があれば `hasError` は不要）
- 必須であるべきpropsをoptionalにしない
- 適切なデフォルト値を設定する（例: `type` のデフォルトは `"text"`）
- 他のコンポーネントのprops型を参照するには `ComponentProps<typeof X>["propName"]` を使用する

### Hooks 依存配列
- `useCallback` / `useEffect` の依存配列にはリンターが求める値をすべて含めること
- 依存配列を減らす目的で `useRef` に最新値を保持するパターンは禁止する
- 再生成の頻度が問題になる場合は、呼び出し側で `useCallback` により参照を安定させること
- 例外: `setInterval` 等のクリーンアップコストが高い `useEffect` 内で、コールバックの最新値が必要な場合のみ `useRef` による保持を許容する。その場合はコメントで理由を明記すること

## ファイル分割
- 責務が大きく複数の関心が混在する場合はコンポーネントを分割する
- ファイル名は内容を適切に表現する汎用的な名前にする

## 一般原則
- SOLID / DRY / KISSを指針として扱う
- ドメイン駆動設計(DDD) を指針として扱う
- クリーンアーキテクチャを指針として扱う
- 今必要でない機能・プロパティは追加しない（YAGNI）
